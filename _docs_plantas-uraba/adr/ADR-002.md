# [ADR-002] Selección del Modelo de Componentes para la Interfaz de Usuario

## Contexto

El proyecto requiere construir una interfaz web para mostrar los resultados de la investigación (plantas de Urabá). Se necesita un sistema de vistas y elementos visuales reutilizables, escalables y eficientes. 

Dado que el proyecto utiliza Bun en el backend como entorno de ejecución y servidor de archivos estáticos ultrarrápido, la arquitectura del frontend debe alinearse con principios de rendimiento óptimo, bajo peso de transferencia y máxima seguridad de los datos ante posibles vulnerabilidades del tipo XSS (Cross-Site Scripting).

No hay un presupuesto asignado para infraestructura compleja ni se desea depender de compiladores pesados o dependencias de terceros propensas a quedar obsoletas.

## Decisión

Adoptar **Web Components Nativos** (`Custom Elements` y `Shadow DOM`) desarrollados de forma **100% programática**, utilizando los métodos estándar del DOM (`appendChild()`, `append()`, `replaceChildren()`, `createElement()`) y **Hojas de Estilos Adoptadas** (`CSSStyleSheet` / `adoptedStyleSheets`). 

Se prohíbe explícitamente el uso de `innerHTML` o manipulación de elementos basados en cadenas de texto raw para garantizar la sanitización nativa de la interfaz.

## Consecuencias

* **Positivas:**
  * **Cero dependencias:** No se requieren librerías como React, Vue o Angular, manteniendo el proyecto agnóstico y con un peso de carga mínimo.
  * **Seguridad atómica (Anti-XSS):** Al construir el árbol mediante nodos (`textContent` y `createElement`), el navegador interpreta los datos estrictamente como texto, eliminando ataques de inyección de código.
  * **Rendimiento y eficiencia en memoria:** `replaceChildren()` limpia y actualiza el DOM de forma óptima. Las hojas de estilo importadas mediante módulos CSS se parsean una sola vez en memoria y se comparten entre múltiples instancias del componente.
  * **Integración limpia con Bun:** Bun sirve los archivos `.js` y `.css` nativos directamente, reduciendo el tiempo de configuración y el tiempo de compilación a cero.

* **Negativas / Desafíos:**
  * **Verbocidad:** Escribir código puramente imperativo con la API de nodos requiere más líneas de código en comparación con plantillas declarativas o JSX.
  * **Curva de aprendizaje:** El equipo debe dominar las APIs nativas modernas del navegador en lugar de abstracciones comerciales.

## Alternativas evaluadas

1. **React en Bun:** Ofrece un desarrollo declarativo ágil y soporte nativo en Bun mediante JSX/SSR. Sin embargo, introduce dependencias externas (`react`, `react-dom`) que añaden peso innecesario y acoplan el código a un ecosistema privado.
2. **Web Components basados en cadenas de texto (`innerHTML`):** Permite escribir HTML de forma más visual en los archivos JS. No obstante, obliga al navegador a parsear texto constantemente en el cliente, degrada el rendimiento de actualizaciones atómicas y abre brechas potenciales de seguridad si se renderizan datos dinámicos sin sanitizar.
3. **Frameworks reactivos ligeros (Lit / Preact):** Reducen la verbocidad del código nativo. Sin embargo, siguen requiriendo la gestión de dependencias externas (npm) y capas de abstracción innecesarias para la escala actual del proyecto de investigación.
